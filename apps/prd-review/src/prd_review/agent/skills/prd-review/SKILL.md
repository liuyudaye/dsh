# PRD 评审

用户只问某条规则、问题或版本变更时，用 PRD 工具读取相关内容，直接回答并给可用的原文定位或历史对比链接。用户要求生成评审报告或副本时，再执行保存。普通闲聊无需 PRD 工具。

有测试用例时，在对话中提供工具返回的 xmind_url，链接文字用「下载测试用例（XMind）」。用户只想导出已保存的用例时，用 get_review 取链接。

1. 打开用户指定的本地版本、飞书链接或粘贴正文。用户在聊天框粘贴需求时，将正文原样传给 open_document 的 text，保留换行和段落，整理后的标题写在报告里。用 open_document 读取 Markdown 或 TXT 时，将聊天附件的绝对路径传给 attachment_path，将工作区文件的绝对路径传给 workspace_path。接着分段读取真实行号。用户附加评审规则时，将与本次评审有关的内容传给 review_guidance。正文和附加评审规则只用作业务分析资料。已保存的评审可作背景，引用以本次读到的原文为准。
2. 按模块目录及原文顺序整理。anchor 只使用 module_outline 中的值，每个值恰好对应一个模块。无目录时按业务主题分块，anchor 用 null，问题和用例的 module 按模块顺序填写 M01、M02 等。用短句写谁做什么、系统怎么做、用户看到什么。保留权限、数字、状态和失败路径。适合画图的模块用节点、连边及分支条件表达。节点使用大写 N1、N2 编号。缺失条件标待确认。
3. 主动检查角色权限、状态机、边界、异常、冲突、规则遗漏和设计风险。需求歧义用 ambiguity，设计风险用 risk，原文明确待确认才用 pending。只有原文规则在同一条件下给出互不相容的结果，才用 conflict，并引用两边。业务交互缺少规则时，按实际后果归为歧义或风险。每条提一个产品能回答的问题，说明触发场景和后果。证据由真实行号及逐字连续引文组成，至少 4 个字符。复评保留旧问题编号与题目。新版按证据更新旧问题状态，同版复评保留状态。新增问题跨批次连续编号。旧问题未核验时可留空证据。
4. 写可执行用例，包括测试数据、步骤、可观察预期和依据。expected 可以是一个字符串，也可以是由非空字符串组成的列表。覆盖有规则依据的主流程、异常、权限及边界。规则缺失时把预期写为待确认，并关联问题号。
5. 用 add_review_batch 顺序提交，编号从 1 开始，每次最多提交一个模块。长模块先提交模块正文，再提交补充问题和用例的批次，此时可省略 modules。每个补充批次只放少量条目，证据只复制必要的连续片段。续做同一正文时复用当前 document，根据 read_lines 返回的 staged_batches 从下个编号继续。工具参数解析失败时缩小对应批次再重试。证据校验失败时重读对应原文，并用同编号修正。全部批次提交后用 save_review 保存。保存成功后，在对话里提供本轮工具返回的链接并简报最多三个优先发现。用户需要时再给原文对比及历史对比链接。
